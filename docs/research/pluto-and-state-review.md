# Pluto 참고와 로컬 상태 인식·자체 평가 검토

검토일: 2026-09-27. 상태: 설계 보완. 게임·학습 모델·OCR·플레이 평가기는 아직 구현하거나 검증하지 않았다. 중요한 검토는 사용자 지정 `gpt-6-astra`, `ultra`로 수행했다.

## 결론과 비용 경계

PlayModel은 **실행·학습·자체 플레이 평가를 모두 로컬에서 수행하고, GPT·유료 토큰 API·외부 LLM 심판을 필수 경로에 넣지 않는다.** 개발자가 설계를 검토할 때 쓰는 Astra는 제품 의존성이 아니다. 로컬 OCR이나 언어 모델 내부의 토큰화는 외부 API 토큰 과금과 관계없다. 전기·저장 공간·하드웨어 비용은 남는다.

라이브러리와 모델 파일을 미리 확보한 뒤에는 API 키 없이 네트워크를 차단해 전체 경로를 검증해야 한다. 모델 자동 다운로드나 클라우드 대체 호출도 차단 대상이다. 선택 게임 자체의 온라인 접속과 이후 YouTube 업로드는 별도 조건이다. 현재 준비 도구의 [pyproject.toml](../../pyproject.toml)은 `dependencies = []`이고 GPT SDK가 없다. 이는 **현재 준비 코드의 사실**이며 미래 프로그램의 오프라인 동작 시험을 대신하지 않는다.

CNN+GRU는 첫 행동 기준선이다. 능력치, 장비, 조건부 효과, 퀘스트 문구까지 이해하는 완성 시스템으로 취급하지 않는다. 관찰·상태 해석·기억·행동·평가를 연결하되 각 부분을 따로 시험하는 구조가 적합하다.

## 정보 조건을 먼저 나눈다

첫 게임 선정 시 `screen_only`와 `api_assisted` 중 정책이 쓸 입력을 고정한다. 전자는 화면·허용된 입력 이력, 후자는 명시적으로 허용된 게임 API 상태를 포함한다. 동일한 점수표에서도 두 실험군 결과는 따로 보고한다. API가 있더라도 숨겨진 상태를 자동으로 허용하지 않는다. 게임별 관측 권한과 필드 목록을 manifest에 남긴다.

화면 정책의 OCR을 시험하려고 API 정답을 **평가기에만** 제공할 수는 있다. 이때 `policy_observation`과 `reference_truth` 저장 경로·접근 권한을 나누고 API 정보가 정책 입력이나 해당 실험의 훈련 특징으로 새지 않는지 검사한다. 평가기가 더 많은 정보를 가진다는 사실도 결과에 표시한다.

## 읽기, 해석, 기억, 행동의 계약

권장 흐름은 `관찰 → HUD/OCR·시각 특징 → 버전 상태·변화 이벤트 → 목표/시간 기억 → 행동 제안 → 기존 단일 입력 writer`다. 게임 전용 상태 정의와 정책 가중치는 별개이며, 새 장르가 생겼다고 기존 정책이 바로 통한다고 가정하지 않는다.

| 부분 | 책임과 경계 |
|---|---|
| 관찰 | 전체 화면의 행동용 축소본과 원본 해상도 HUD ROI를 연결한다. 작은 글자를 320×180 입력에서만 읽도록 제한하지 않는다. 해상도·UI 배율·언어·ROI 버전을 기록한다. |
| 읽기 | 숫자 전용 인식기, 아이콘/게이지 판독, 일반 OCR을 필요에 따라 조합한다. Tesseract는 로컬 실행과 TSV의 위치·`conf`·`text` 출력을 지원하는 후보다. 게임 폰트·한국어 정확도는 별도 시험 대상이다. [공식 OCR 사용법](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html) |
| 상태 | 정규화된 값과 원문·출처·시간을 함께 보관한다. 읽을 수 없는 값은 0으로 채우지 않는다. `unknown`, `fresh`, `stale`, `conflicted`를 구분한다. |
| 의미 해석 | 첫 게임의 필드 사전·문구 템플릿·메뉴 상태기계로 시작한다. 범위가 넓어지면 라벨을 갖춘 의미 인코더를 비교한다. 자유로운 문장 이해가 실제로 필요하면 로컬 언어 모델을 별도 후보로 시험한다. |
| 기억·계획 | 최근 관찰과 확인된 이벤트, 미해결 목표를 보관한다. 관측되지 않은 사실을 확정하지 않는다. 장기 목표가 필요한 게임에서만 상위 계획기와 저수준 행동 정책을 분리해 비교한다. |

최소 관측 계약은 `schema_version, game_profile_version, entity_id, field_id, value, value_type, unit, raw_text, roi, source_frame_id, observed_at, available_at, extractor_version, confidence, calibration_id, valid_until, status, source_mode`다. 상태 스냅샷에는 원본 관측 ID를 남긴다. confidence는 엔진 점수이며 보정된 성공 확률로 가정하지 않는다. 게임별 보류 기준과 보정 결과를 버전으로 관리한다.

행동 시점에 아직 계산되지 않은 OCR 결과는 그 행동의 입력으로 사용할 수 없다. 오래 걸리는 OCR은 비동기로 실행하되 관찰 시각과 사용 가능 시각을 모두 유지한다. 정책은 누락 여부·관측 나이를 입력받고, 오래된 텍스트 응답이 새 메뉴의 상태를 덮어쓰지 못하게 한다. 중요 상태가 불확실하면 확인 행동·정지·사람 검토 중 게임별 대안을 선택한다.

## 능력치 상승과 문장의 의미

`delta = normalize(after) - normalize(before)`는 같은 캐릭터·능력치·단위·해석 버전이고 두 값이 유효할 때만 만든다. 변화 이벤트에는 전후 관측, 신뢰 상태, 적용 시각 범위, 원인 후보를 연결한다. 관측 간격에서 여러 사건이 일어났으면 단일 원인을 확정하지 않는다.

예를 들어 공격력 100→110은 **표시값 변화**다. 레벨 상승, 장비 교체, 일시 버프, 기본 능력치, 지역 효과 중 원인은 게임 규칙과 추가 관측으로 구별해야 한다. 모든 게임에 `기본+장비+버프`라는 선형식을 적용하지 않는다. 소수점 반올림, 합산 순서, 퍼센트 보정, 최대값 변경도 별도 규칙이다. 표시 정밀도가 부족하면 정확한 증가량 대신 구간이나 미확정을 저장한다.

문자 인식은 의미 이해가 아니다. “공격력 +10”이 장착된 장비의 적용 효과인지 상점 미리보기인지 먼저 판단해야 한다. “획득 가능”과 “획득 완료”, “효과 없음”, “체력 50% 이하일 때”, 현재 HP와 최대 HP는 서로 다른 상태다. 텍스트와 화면 위치·메뉴 맥락을 함께 라벨링하고, 지원하지 않는 문장은 보류한다. 원문을 그대로 명령으로 실행하는 인터페이스도 만들지 않는다.

캐릭터 성장 지표와 정책 실력 지표는 분리한다. 장비가 좋아져 승률이 높아졌다면 같은 장비·난이도·시작 상태에서 정책을 다시 비교해야 한다. 성장 목표 자체를 측정하는 실험은 허용하지만 그 결과를 조작 능력 향상으로 바꾸어 보고하지 않는다.

## 자체 플레이와 평가·재학습

- **자체 플레이:** 저장된 정책이 실제 게임을 조작하고 관찰·제안·실제 입력·결과를 기록한다.
- **자체 평가:** 로컬 평가기가 그 기록을 고정된 기준으로 채점한다. 자동 채점의 정확도 자체도 독립 정답으로 검증한다.
- **자기 대전:** 같은 계열의 정책 또는 과거 정책이 상대가 되어 경기를 생성한다. 대전 환경이 지원될 때 선택하는 학습 방식이다.

평가 지표는 게임별로 승패, 목표 달성, 사망, 진행도, 자원 효율, 개입·실패·중단 등을 정한다. 정책 자신의 승률 예측이나 자유 형식 자기 평가는 진단 자료로만 둔다. 정답은 허용된 종료 신호, 검증된 화면 판정, 별도 API 심판 또는 사람이 라벨링한 표본에서 얻는다. 중단을 성공 분모에서 빼거나 판독 실패를 승리로 바꾸지 않는다.

평가기 버전과 기준선을 고정하고, 세션 단위 holdout에서 결과 판정의 오탐·미탐·보류율을 측정한다. 정책이 점수만 올리는 반복 행동, 같은 보상 이벤트 중복 수집, 메뉴 숫자 조작 같은 우회를 별도 사례로 시험한다. 학습 보상과 최종 평가 지표를 구분하고, 점수 증가가 실제 목표 개선인지 확인한다.

오인식 의심 구간은 재학습 큐에서 격리한다. 사람 검토와 원본 프레임 재판독 뒤에 새 라벨 버전을 만든다. AI가 스스로 보낸 입력을 자동으로 정답 BC 라벨로 쓰지 않는다. 사람 교정은 검토된 BC 데이터가 되고, AI rollout은 별도 출처를 갖는 평가·RL 후보 데이터가 된다. 자기 플레이 영상만으로 선택하지 않은 행동의 결과를 알 수 없으므로, 영상 재생을 반사실적 RL 환경으로 취급하지 않는다.

## 구현 전 통과 조건

아래는 **시험 계획**이다. 달성한 성능이나 보장 수치가 아니다. 게임 선정 때 평가 표본과 임계값을 정하고 후보 모델 결과를 보기 전에 고정한다.

| 게이트 | 시험 자료·통과 증거 |
|---|---|
| L0 오프라인 | 필요한 파일을 로컬에 둔 상태에서 API 키 없이 네트워크 차단 후 기록→추론→학습→평가 한 주기를 실행한다. 외부 요청·자동 다운로드·외부 judge 의존성이 없어야 한다. |
| L1 숫자·관측 | 별도 세션의 숫자 라벨, 혼동 숫자·음수·소수·퍼센트, 가림·블러·다른 UI 배율을 시험한다. 필드 정확도와 보류율을 함께 보고하고 낮은 신뢰·누락·만료값이 확정 상태로 승격되지 않는지 확인한다. |
| L2 변화·의미 | 레벨업, 장비 미리보기/실장착, 버프 생성/만료, 최대 HP만 변경, 반올림, 변화 없음, 중복 프레임, 조건·부정 문구를 포함한다. 값 변화와 원인 판정·이벤트 중복 억제를 따로 채점한다. |
| L3 자체 평가 | 사람 또는 독립 신호 정답과 비교해 성공·실패·중단 판정 정확도와 혼동표를 만든다. 미지 문구·OCR 오류·보상 반복에 대한 보류와 오탐을 검토하고 정책 점수와 평가기 신뢰도를 별도 보고한다. |
| L4 개선 판정 | 같은 입력 조건·캐릭터 조건의 기준 정책과 후보를 고정 평가 세션/시드에서 비교한다. holdout 재학습 유출, 자가 BC 라벨 유입, 기존 능력 퇴행 여부를 확인한 뒤에만 후보를 승인한다. |
| L5 자원·제어 | 게임·OCR·정책·녹화 동시 실행의 RAM/VRAM, p50/p95/p99 지연, 관측 나이, 큐 누적, 입력 해제·사람 개입을 측정한다. 예산 초과 시 기능·빈도를 조정하며 목표 수치는 측정 전에 게임 프로필에서 정한다. |

호스트의 GTX 1660 SUPER는 6144 MiB VRAM으로 확인되었지만 OCR·정책·언어 모델 동시 실행과 학습은 미검증이다. CPU OCR, ROI별 낮은 갱신 빈도, 모델 분리부터 비교한다. Pluto의 양자화된 추론 배포 규모로 우리 학습 메모리나 범용 언어 이해 능력을 추정하지 않는다. 6 GB에서 거대 통합 모델이 필요하거나 충분하다는 결론 모두 피한다.

첫 게임에서 확정할 입력은 게임/플랫폼, 화면 전용 여부, 언어·UI 조건, 필요한 능력치와 문구, 성공 기준, 재시작 가능한 시나리오다. 이는 현재 준비 문서 완성을 막는 항목이 아니라 실제 구현·데이터 수집의 시작 조건이다. 결정은 [ADR 0004](../decisions/0004-local-state-and-self-evaluation.md)에 고정한다.
